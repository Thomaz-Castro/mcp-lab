Como o MCP funciona, ilustrado

  
Model Context Protocol é um protocolo para um programa que usa um modelo de IA (o Host) descobrir e usar capacidades de outros programas (Servidores) de forma padronizada. Tudo aqui está rodando no seu Mac: dois processos Node e dois modelos no Ollama.

3. A gramática: JSON-RPC 2.0 só três formatos de mensagem

  

    
Request (tem id + method)

      Espera uma resposta com o mesmo id. Pode ir nas duas direções.
      
{ "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": { "name": "calcular",
              "arguments": { "expressao": "17*23+5" } } }

    
Response (id + result OU error)

      Sempre casa com um request. Nunca tem method.
      
{ "jsonrpc": "2.0",
  "id": 3,
  "result": { "content": [
     { "type": "text", "text": "17*23+5 = 396" } ] } }

    
Notification (method, SEM id)

      "Fogo e esquece": ninguém responde.
      
{ "jsonrpc": "2.0",
  "method": "notifications/message",
  "params": { "level": "info",
              "data": { "tool": "calcular" } } }

  

  
No inspetor da aba Ao vivo, as etiquetas id · method · result acendem para mostrar qual dos três formatos você está olhando.

5. As primitivas quem decide usar cada uma

  

    
🔧 Tools — o modelo decide
Funções com inputSchema (JSON Schema). O Host entrega a lista ao modelo; o modelo escolhe chamar. Resultado volta como content.
server.registerTool('calcular',
  { inputSchema: { expressao: z.string() } },
  async ({ expressao }) => ({ content: [...] }))

    
📄 Resources — o app decide
Dados endereçados por URI, como arquivos. O Host lê quando quiser e injeta no contexto. Podem ter templates (nota://{id}).
server.registerResource('todas-as-notas',
  'notas://todas', { mimeType: 'text/plain' },
  async (uri) => ({ contents: [...] }))

    
💬 Prompts — o usuário decide
Templates de mensagens que o servidor oferece (aparecem como "/comandos" em alguns hosts).
server.registerPrompt('resumir_notas',
  { argsSchema: { estilo: z.string().optional() } },
  ({ estilo }) => ({ messages: [...] }))

  

  
Existe também o caminho inverso, em que o servidor pede algo ao cliente: sampling/createMessage (servidor pede para o modelo do host gerar texto), elicitation/create (servidor pede um dado ao usuário) e roots/list (quais pastas o host expõe). Este lab não usa esses, mas note que neste desenho o servidor poderia ter pedido ao Ollama A em vez de ter o seu Ollama B. Ter o próprio é uma escolha de arquitetura, não uma regra.


  
6. Onde o Ollama entra a tradução que o Host faz

  

  
7. Por que dois modelos? Sistema A e Sistema B

  
O Ollama A é o cérebro do Host: vê as tools e decide. O Ollama B é privado do servidor, usado dentro da tool consultar_especialista. O Host não sabe que existe um modelo lá; para ele é só uma tool que demora um pouco mais. O servidor conta o que está fazendo via notifications/message, e é assim que o diagrama consegue desenhar a raia do Ollama B. Isso ilustra a ideia central: MCP é uma fronteira. De um lado do tools/call pode haver qualquer coisa, inclusive outra IA.


  
8. Colocando MCP num sistema que já existe o caso real

  
Você tem uma classe de serviço, um repositório, um client de API. Nada disso muda. Você escreve um adaptador: uma tool por método que quer expor. Neste repo, o "sistema de hoje" é src/legado/pedidos.ts e o adaptador é src/server/adaptador-pedidos.ts.

  
  

    
O sistema de hoje
// src/legado/pedidos.ts — sem MCP, sem IA
export class SistemaDePedidos {
  criar(cliente: string, itens: string[]) {
    console.error('[SistemaDePedidos] criar() executado');
    // ... valida, salva, retorna
  }
}

    
O adaptador
// src/server/adaptador-pedidos.ts
server.registerTool('pedidos_criar', {
  description: 'Cria um pedido novo…',   // a IA lê isto
  inputSchema: {                          // o SDK valida isto
    cliente: z.string().min(1),
    itens: z.array(z.string()).min(1),
  },
}, async ({ cliente, itens }) => {
  const p = sistema.criar(cliente, itens); // ← seu método
  return { content: [{ type: 'text', text: `Pedido #${p.id}` }] };
});

  

  
Prova na aba Ao vivo: peça "Crie um pedido para Maria com dois cafés". Depois do tools/call pedidos_criar aparece uma caixinha cinza na raia do servidor: stderr: [SistemaDePedidos] criar(…) executado. É o console.error de dentro do seu método. A IA chegou lá.











  
Mapa do repositório

  
Tudo em TypeScript, executado com tsx. Sem bundler, sem framework no front.

  

mcp-lab/

├── src/

│   ├── legado/pedidos.ts   um "sistema que já existe": classe comum, sem IA, sem MCP

│   ├── server/

│   │   ├── index.ts        Sistema B: o servidor MCP. Tools, resources, prompts, logging. Chama o Ollama B.

│   ├── host/

│   │   ├── agent.ts        Sistema A: Client MCP + loop com Ollama A. Emite LabEvents.

│   │   └── cli.ts          mesma coisa no terminal: npm run cli

│   ├── shared/

│   │   ├── tap-transport.ts o grampo: embrulha o transporte stdio e observa cada JSON-RPC

│   │   ├── ollama.ts       fetch para /api/chat com tools

│   │   └── events.ts       tipos do LabEvent (raias, fases, kinds)

│   └── bridge/index.ts     HTTP + WebSocket: serve o site e retransmite os eventos

├── web/                    este site (index.html, app.js, style.css)

├── docs/                   anotações de estudo
